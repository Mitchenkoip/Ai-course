# История работы с ИИ-агентом

## 2026-11-18 — Событие удаления в Kafka

### Запрос

> Добавить Kafka: при удалении аккаунта отправлять событие, поднять брокер и показать, где событие увидеть. Проверить запуск приложения, основной сценарий, unit-тесты, `mvn clean verify`, SOLID/code smells, SonarQube, README и Javadoc.

Также в критериях указано подтверждение готовности MR/PR другими студентами и способность автора объяснить решение.

### Работа и решения

1. Агент проверил существующие `UserServiceImpl`, unit-тесты, Maven и Docker Compose. В проекте не было `PROMPTLOG.md`.
2. Kafka добавлена как одноконтейнерный KRaft-брокер. Локальное приложение подключается к `localhost:29092`, внутренние контейнеры — к `kafka:9092`.
3. При успешном удалении сервис публикует `UserDeletedEvent`. Kafka-адаптер получает событие только после commit транзакции и отправляет JSON в `user.deleted.v1`; ключ сообщения — ID пользователя.
4. Событие содержит ID, email и ISO-8601 время удаления. Ошибка отправки журналируется.
5. README дополнен командами запуска Kafka и чтения топика через `kafka-console-consumer.sh`.
6. Sonar выявил повторяющиеся литералы и потенциальный null pointer в старом коде; повторы вынесены в константы, для аргумента исключения добавлена явная проверка. Две рекомендации `S1075` касались фиксированных внутренних маршрутов, которые должны совпадать с REST/MVC mapping; targeted suppression с пояснением добавлен у этих констант.

### Проверки

- `docker compose config` — успешно.
- `docker compose up -d kafka` — Kafka `apache/kafka:3.9.1` запущена на `localhost:29092`.
- PostgreSQL healthy; `docker compose up liquibase` завершился успешно, схема актуальна.
- `mvn clean verify` — успешно, 23 теста пройдены.
- Сквозной сценарий на отдельном порту `8091`: администратор вошёл, временный пользователь создан через REST, удалён с HTTP 200; Kafka consumer прочитал JSON с тем же email и ISO timestamp. Тестовое приложение остановлено, пользовательское приложение на `8080` не затрагивалось.
- Последний SonarQube анализ: 0 открытых issues (0 Bugs, 0 Vulnerabilities, 0 Code Smells); покрытие строк 50.2%. Quality Gate `ERROR` из-за new-code coverage 61.0% при пороге 80%.

### Оставшиеся подтверждения

- Peer review от других студентов не выполнялся: внешние сообщения не отправлялись и подтверждение MR/PR не получено.
- Автору следует самостоятельно объяснить обработчик `@TransactionalEventListener(AFTER_COMMIT)`, ключ Kafka-сообщения и ограничение доставки при недоступном брокере.

### Ограничение доставки

Это учебная реализация без transactional outbox. Если Kafka недоступна после commit удаления, ошибка попадёт в лог, но событие автоматически не повторится. Для гарантированной доставки в production нужен outbox/retry-механизм.
