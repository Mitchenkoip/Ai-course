# Java AI Training Project

Учебный репозиторий для практического освоения Java-разработки с использованием ИИ-агентов.

## Цель

Основная задача студента - реализовать техническое задание, используя современные ИИ-агенты как основной инструмент разработки.

Допускается использование любых ИИ-агентов: Codex, Kilo Code, Windsurf, Cursor, Claude Code, GitHub Copilot и других.

Основной акцент сделан на умении грамотно формулировать задачи ИИ, проверять результат и доводить проект до рабочего состояния.

---

## Структура проекта

```
docs/
```

Папка с подробным техническим заданием, которое необходимо реализовать.
Задача: Разработать админ панель.


```
infra/
```

Инфраструктура проекта.

Содержит Docker Compose и все необходимые файлы для автоматического запуска локальной базы данных PostgreSQL.

Также запускает Kafka для публикации событий удаления пользователей.

После запуска инфраструктуры автоматически:

* создается пользователь базы данных;
* создается база данных;
* создается схема приложения;
* выполняются миграции;
* загружаются тестовые данные.

Дополнительная настройка базы данных не требуется.

---

## Порядок работы

1. Запустить инфраструктуру из каталога `infra`.
2. Дождаться успешного завершения инициализации базы данных.
3. Реализовать проект, используя ИИ-агента.
4. Проверить соответствие результата требованиям технического задания.

Команды запуска инфраструктуры:

```bash
cd infra
docker compose up -d
docker compose ps
docker compose logs liquibase
```

PostgreSQL должен остаться запущенным, а контейнер Liquibase после успешного применения миграций должен завершиться без ошибки.

## Сборка и запуск приложения

Команды выполняются из корня проекта после успешного запуска инфраструктуры:

```bash
mvn clean verify
java -jar target/spring-boot-security-demo-0.0.1-SNAPSHOT.jar
```

Приложение использует `http://localhost:8080`. Откройте этот адрес: неавторизованный пользователь будет перенаправлен на страницу входа. Если порт 8080 занят, найдите процесс, который его использует, либо запустите приложение на временном порту:

```bash
java -jar target/spring-boot-security-demo-0.0.1-SNAPSHOT.jar --server.port=8081
```

Для проверки сценариев используются тестовые записи, загружаемые Liquibase (пароль у всех — `password`):

| Роль | Email | Проверка |
|---|---|---|
| `ROLE_ADMIN` | `testuser3@example.com` | `/admin`, просмотр, добавление, редактирование и удаление пользователей |
| `ROLE_USER` | `testuser1@example.com` | `/user`; попытка открыть `/admin` или изменять пользователей должна быть запрещена |

После входа под администратором проверьте добавление пользователя, затем Edit (измените поле и сохраните) и Delete (подтвердите удаление). Под обычным пользователем проверьте страницу `/user` и отсутствие доступа к административным операциям. Для просмотра диагностики инфраструктуры:

Администратор не может удалить собственную активную учётную запись: для проверки удаления выберите другую строку таблицы. Это сохраняет доступ к панели и тестовым сценариям.

```bash
cd infra
docker compose ps
docker compose logs liquibase
```

В `docker compose ps` PostgreSQL должен иметь состояние `healthy`. Liquibase — одноразовый сервис: после применения changeset контейнер завершается; успешный результат подтверждается сообщением `Update has been successful` в его логах.

## Unit-тесты и покрытие

Unit-тесты выполняются без Spring-контекста и без PostgreSQL:

```powershell
mvn test
```

Эта команда запускает unit-тесты, но не формирует отчёт покрытия JaCoCo.

Полная проверка также запускает тесты и формирует отчёт JaCoCo:

```powershell
mvn clean verify
```

После `verify` HTML-отчёт находится в `target/site/jacoco/index.html`, XML-отчёт — в `target/site/jacoco/jacoco.xml`. Результаты отдельных тестов Maven сохраняет в `target/surefire-reports`.

## Событие удаления в Kafka

Для запуска приложения нужны PostgreSQL с применёнными миграциями и Kafka. Из каталога `infra` поднимите зависимости:

```powershell
cd infra
docker compose up -d postgres kafka
docker compose up liquibase
docker compose ps
cd ..
```

Kafka слушает порт `29092` на компьютере разработчика; приложение использует `localhost:29092`. При старте приложения создаётся топик `user.deleted.v1`.

`UserServiceImpl` не знает о Kafka: после удаления он публикует `UserDeletedEvent` через Spring `ApplicationEventPublisher`. Отдельный Kafka-адаптер обрабатывает это событие в фазе `AFTER_COMMIT` и отправляет его через `KafkaTemplate`. Так событие не уйдёт, если транзакция удаления откатится.

Чтобы увидеть события, откройте отдельный терминал в каталоге `infra` и запустите consumer **до удаления**:

```powershell
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 `
  --topic user.deleted.v1 `
  --from-beginning
```

Теперь войдите в админ-панель, удалите пользователя, который не является текущим администратором, и наблюдайте за терминалом consumer. Появится JSON с `userId`, `email` и `deletedAt`. Остановить просмотр можно сочетанием `Ctrl+C`. Событие публикуется только после успешного commit удаления в PostgreSQL; ключ Kafka-сообщения — ID пользователя.

Пример сообщения:

```json
{"userId":10,"email":"deleted@example.com","deletedAt":"2026-11-18T10:12:52Z"}
```

Это учебная отправка события после commit. Если брокер недоступен, ошибка отправки попадёт в лог приложения, но событие автоматически не повторяется; для гарантированной доставки в production обычно используют transactional outbox.

## Анализ SonarQube

Для локального SonarQube запустите только его сервис из каталога `infra` (это не запускает PostgreSQL):

```powershell
cd infra
docker compose up -d sonarqube
docker compose ps sonarqube
cd ..
```

Создайте токен в SonarQube (`http://localhost:9000`), задайте его в переменной окружения и запустите анализ из корня проекта:

```powershell
$env:SONAR_TOKEN = "<токен SonarQube>"
try {
    mvn clean verify org.sonarsource.scanner.maven:sonar-maven-plugin:3.11.0.3922:sonar `
      "-Dsonar.host.url=http://localhost:9000" `
      "-Dsonar.token=$env:SONAR_TOKEN"
} finally {
    Remove-Item Env:SONAR_TOKEN -ErrorAction SilentlyContinue
}
```

JaCoCo формирует XML на фазе `verify`. Параметр `sonar.coverage.jacoco.xmlReportPaths` уже настроен в `pom.xml` на `target/site/jacoco/jacoco.xml`, поэтому Maven Sonar Scanner импортирует покрытие из этого файла при анализе.
Откройте результат анализа в разделе проекта SonarQube после завершения фоновой обработки. Если `clean` сообщает, что файл в `target` занят, остановите процесс, который использует этот файл (например, локальный сервер отчёта), и повторите команду.

## Наставление студентам

Вы уже решали эту задачу ранее. Техническое задание в основном не изменилось: вместо локального MySQL и ручного выполнения SQL-скриптов теперь используется PostgreSQL, Liquibase и Docker Compose, чтобы база данных поднималась автоматически и одинаково у всех. В остальном логика приложения, роли, экраны, REST API, валидация и критерии приемки остались теми же.

ТЗ в каталоге `docs` расписано очень подробно. Его достаточно для точного решения задачи без самостоятельного изменения постановки. Ваша задача сейчас - не "угадать", как должно работать приложение, а научиться управлять ИИ-агентом так, чтобы он последовательно реализовал требования.

Попробуйте разные стратегии:

* решать задачу по шагам: сначала инфраструктура и конфигурация, затем сущности и БД, потом Security, REST API, UI и финальная проверка;
* решать задачу крупным запросом целиком, а затем просить агента проверить результат по каждому разделу ТЗ;
* комбинировать подходы: дать агенту общий контекст, но просить реализовывать и коммитить небольшими законченными частями.

Хорошая практика - просить агента не только писать код, но и сверять результат с критериями приемки. Если агент предлагает изменить требования, сначала проверьте ТЗ. Требования менять нельзя без явного согласования.

Ведите prompt log: сохраняйте важные промпты, ответы агента, найденные ошибки и решения. Это поможет понять, какие формулировки работают лучше, а какие приводят к неполному или неверному результату.

Делайте частые локальные коммиты. Коммит после каждого законченного этапа позволяет спокойно экспериментировать с промптами, откатываться к рабочему состоянию и сравнивать разные варианты решения.

Фиксируйте промежуточные результаты: что уже реализовано, какие проверки прошли, какие ошибки остались, какие вопросы нужно уточнить. Это дисциплинирует работу с ИИ и помогает не потерять контекст.

Главная цель упражнения - поэкспериментировать с промтингом и промпт-инжинирингом на реальной инженерной задаче. Чем точнее вы ставите задачу, тем легче проверить результат и довести проект до рабочего состояния.
